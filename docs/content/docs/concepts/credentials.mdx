Many kubeconfig files hold a token or a private key in plain text. Anyone, or
any program, that can read the file can use your access. tug's rule is
simple: **a secret lives only in your OS keychain**.

## Where secrets go

| Platform | Default store |
| --- | --- |
| macOS | Keychain |
| Windows | Credential Manager |
| Linux | Secret Service (GNOME Keyring, KWallet and others) |
| Anywhere, if you choose | An encrypted file (see below) |

Secrets that end up in the keychain:

- Tokens, client keys and certificates **found in kubeconfig files** when you
  import them. tug copies them in; your original file is left as it was.
- **API tokens** that providers such as Akamai and CoreWeave ask for. tug
  asks once, when you import, and never again.
- **Short-lived credentials** that providers hand out, cached until a minute
  before they expire.
- **Sign-in tokens** for clusters that trust an OpenID Connect issuer: the
  refresh token and ID token from [`tug auth login`](/docs/guides/sign-in).
- **Model providers' API keys** for [`tug why --deep`](/docs/guides/ai-explanations),
  one per provider, from `tug intelligence key set`.

All entries are filed under the service name `tug`.

## How kubectl gets a credential

Every kubeconfig tug writes uses Kubernetes' standard "exec" mechanism. In
place of a token it says: *to get a credential, run `tug auth token`*.

<Flow caption="This happens in the background whenever a client needs to log in.">
  <FlowStep title="kubectl" tone="harbour">
    Reads the session kubeconfig and runs `tug auth token --cluster …`.
  </FlowStep>
  <FlowStep title="tug auth token" tone="tug">
    Looks for a cached credential that is still good.
  </FlowStep>
  <FlowStep title="Keychain">
    Returns it, or…
  </FlowStep>
  <FlowStep title="Provider" tone="safe">
    …tug asks the provider for a fresh one and caches it.
  </FlowStep>
</Flow>

This works for kubectl, helm, k9s, client libraries and anything else that
understands kubeconfig files. You can try it yourself:

```bash
tug auth token --cluster prod-eu            # prints an ExecCredential as JSON
tug auth token --cluster prod-eu --refresh  # skip the cache and ask the provider
```

<Callout type="info" title="Newer kubectl versions and kuberc">
  Newer kubectl versions can restrict which credential plugins may run, using a
  `kuberc` file. If yours has an allowlist, add tug to it.
  [`tug doctor`](/docs/guides/doctor) checks this for you and says exactly
  what to change.
</Callout>

## No keychain? Use the encrypted file

Servers, containers and CI runners often have no keychain. tug can keep
secrets in a single file encrypted with AES-256-GCM instead. Choose it with
two environment variables:

```bash
export TUG_KEYRING_BACKEND=file
export TUG_KEYRING_PASSPHRASE='a long passphrase from your secret manager'
```

The file is `secrets.enc` in tug's data folder. With the default backend,
`auto`, tug uses the keychain when there is one, and falls back to the file
only when `TUG_KEYRING_PASSPHRASE` is set. You can also set the backend in
[`config.yaml`](/docs/reference/configuration).

| Backend | Behaviour |
| --- | --- |
| `auto` (default) | Keychain if it works; otherwise the encrypted file, if a passphrase is set; otherwise an error that says what to do. |
| `keychain` | Keychain only. |
| `file` | Encrypted file only. Needs `TUG_KEYRING_PASSPHRASE`. |

## Other kinds of credential

Providers can hand out more than tokens:

| Kind | Example | What tug does |
| --- | --- | --- |
| Token or client certificate | EKS, GKE, LKE, kubeconfig files | Caches it in the keychain until shortly before it expires. |
| OpenID Connect | CoreWeave with `auth=oidc` | Signs you in to the issuer and refreshes the ID token. See [Signing in](/docs/guides/sign-in). |
| Another exec plugin | `kubelogin`, `gke-gcloud-auth-plugin` in a kubeconfig | Runs it unchanged when a credential is needed. |

When a credential may have leaked, [`tug auth rotate`](/docs/guides/rotating)
replaces it, for providers that support rotating.

## Removing stored secrets

`tug forget <provider>/<account>` deletes a source's credentials from the
store along with its clusters. See [Uninstalling](/docs/getting-started/uninstalling)
to remove everything.
