These commands act on a **workload** (a deployment, statefulset or daemonset)
or a single pod, in your session's namespace. Every one takes a
[fuzzy name](/docs/concepts/targets), so `api` finds `deploy/api-server`, and
every one accepts `-n <namespace>` to look somewhere else.

## Logs

```bash
tug logs api                 # last 10 lines from each pod of deploy/api-server
tug logs api -f              # keep following, including pods that start later
tug logs api -f --since 10m  # only the last ten minutes, then follow
tug logs sts/db -c postgres  # one container
tug logs api --json          # pretty-print lines that are JSON objects
```

For a workload, tug reads **every pod** at once and puts a coloured
`pod/container` prefix in front of each line, so you can tell them apart:

```text
api-server-7d9c-xk2p/api GET /healthz 200 1ms
api-server-7d9c-m4qz/api POST /v1/orders 201 42ms
```

With `-f`, pods that start later (during a rollout, say) join the stream
automatically. Press <kbd>Ctrl</kbd>+<kbd>C</kbd> to stop.

| Flag | What it does |
| --- | --- |
| `-f`, `--follow` | Keep streaming, including new pods. |
| `-c`, `--container` | Only this container. |
| `--tail <n>` | Lines from the end of each log. Default: all for a pod, 10 for a workload. |
| `--since <duration>` | Only lines newer than this, such as `10m` or `2h`. |
| `-p`, `--previous` | The previous container's logs, after a crash or restart. |
| `--timestamps` | Add timestamps. |
| `--json` | Pretty-print lines that are JSON objects. |

## A shell in a pod

```bash
tug sh api                   # bash if the image has it, otherwise sh
tug sh api -c sidecar        # a particular container
tug sh api -- env            # run one command instead of a shell
tug sh pod/debug -- cat /etc/resolv.conf
```

For a workload, tug picks one of its running, ready pods and tells you which:

```text
pod/api-server-7d9c-xk2p, container api; exit to leave
root@api-server-7d9c-xk2p:/app#
```

The exit code of a command you run is passed back, so `tug sh api -- test -f /ready`
works in scripts.

<Callout type="info">
  Opening a shell can change things inside the pod, so on a
  [read-only session](/docs/concepts/read-only) tug asks before it opens one.
</Callout>

### Images without a shell

Distroless and scratch images have no shell at all. For those, `tug sh` offers
to add an **ephemeral debug container** to the pod: a small container that
shares the app container's processes, so you can look around while it runs.
The app's own files are under `/proc/1/root`.

```bash
tug sh pod/scratch                          # offers a debug container
tug sh pod/scratch --image nicolaka/netshoot # bring your own tools (default: busybox:1.36)
```

A debug container stays in the pod until the pod is replaced, and adding one is
a change to the cluster, so tug asks first and a read-only session asks again.

## Port-forwarding

```bash
tug pf api 8080              # localhost:8080 → container port 8080
tug pf api 9000:8080         # localhost:9000 → container port 8080
tug pf api 9000:http         # localhost:9000 → the port named "http"
tug pf db                    # every port the pod declares, on the same local port
tug pf api 8080 --address 0.0.0.0   # listen on all interfaces, not just localhost
```

```text
deploy/api-server via pod/api-server-7d9c-xk2p; Ctrl-C to stop
```

Port-forwarding only reads, so it works on read-only sessions without asking.

### Keep a forward running in the background

A normal forward ends when you press <kbd>Ctrl</kbd>+<kbd>C</kbd>, or when its
pod goes away. Give it a name and [tugd](/docs/guides/proxy) runs it for you
instead: it keeps the same local port and reconnects to a new pod whenever the
old one is replaced.

```console
$ tug pf db 5432 --name db
Forwarding localhost:5432 -> 5432 to sts/db (pod/db-0) as db
$ tug pf ls
NAME   CLUSTER      NAMESPACE   TARGET   PORTS       STATE        RESTARTS   SINCE
db     staging-us   data        sts/db   5432:5432   forwarding   0          2m
$ tug pf stop db
Stopped db
```

While a pod is being replaced, the state reads `reconnecting`. `tug pf stop
--all` ends every named forward, and tugd keeps running while any is open.

## Why isn't it working?

`tug why` reads everything Kubernetes knows about a workload and tells you, in
plain words, what's wrong and what to try next: crashing containers (with the
last exit code), images that won't pull, containers running out of memory,
missing ConfigMaps or Secrets, failing probes, pods no node can take, volume
claims stuck in Pending, and recent warning events.

```console
$ tug why billing
deploy/billing in shop is not ready: 0/1 ready

POD                  STATUS             READY   RESTARTS   NODE     AGE
billing-5d4f-x2x4z   CrashLoopBackOff   0/1     7          node-1   3h

error    pod/billing-5d4f-x2x4z, container main: CrashLoopBackOff
         keeps crashing and waits to restart; last exit code 1 (Error)
         next: read the crashed container's logs:
               tug logs pod/billing-5d4f-x2x4z --previous -n shop

Recent warning events:
LAST SEEN   OBJECT                   REASON    MESSAGE
2m (x31)    pod/billing-5d4f-x2x4z   BackOff   Back-off restarting failed container main in pod billing-5d4f-x2x4z
```

The command to try next gets a line of its own, so you can copy it straight
into your shell.

It works for deployments, statefulsets, daemonsets, jobs and pods
(`tug why job/migrate`), and only ever reads. A healthy workload gets
"Nothing wrong found." Use `-o json` or `-o yaml` to feed the findings to
another tool.

When the cause still isn't clear, `tug why billing --deep` asks a model you
choose to explain the same evidence and the end of the failing containers'
logs, after showing you exactly what it will send and what it may cost. It is
off until you turn it on; see [AI explanations](/docs/guides/ai-explanations).

### Custom resources and other kinds

Name any other kind as kubectl does, by its plural, singular or short name,
with its group when two APIs share a name: `certificate/web-tls`,
`db/orders`, `kustomization.kustomize.toolkit.fluxcd.io/apps`. For an
operator's resource, the useful question is why its desired state hasn't
converged, so `tug why` reads:

- its status conditions. `Ready=False`, `Stalled=True` and the like are
  errors, and so are conditions such as Cluster API's `ControlPlaneReady=False`
  or a node's `MemoryPressure=True`;
- whether its controller has caught up with its latest change
  (`status.observedGeneration` behind `metadata.generation`);
- everything it owns, found through ownerReferences, with the usual diagnosis
  for each workload it owns and the conditions of everything else;
- recent warning events about all of it.

```console
$ tug why db/orders
database/orders in shop is not ready: BackupFailing: the latest backup failed (owns 2, 1 not ready)

CONDITION   STATUS   REASON          SINCE
Ready       False    BackupFailing   10m

error    database/orders: BackupFailing
         Ready is False: the latest backup failed
         next: see its status and events:
               tug describe databases.db.example.com/orders -n shop

error    backup/orders-nightly: UploadFailed
         Ready is False: bucket "orders-backups" not found
         next: see why:
               tug why backups.db.example.com/orders-nightly -n shop

Recent warning events:
LAST SEEN   OBJECT            REASON         MESSAGE
2m (x3)     database/orders   BackupFailed   backup orders-nightly failed
```

A cronjob is judged by its newest job, so an old failure kept in its history
doesn't count against it. A cluster-scoped resource, such as a Crossplane
composite, is searched across the whole cluster for what it owns, which can
take a few seconds on a large one. When tug may not list a resource, it says
which, since anything of that kind would be missing.

## What is it made of?

`tug tree` shows a workload and everything around it, with the health of each
part: its ReplicaSets (or revisions), pods and containers, the Services that
send traffic to it, and the ConfigMaps, Secrets and volume claims its pods use.

```console
$ tug tree checkout
deploy/checkout                  ✓ 2/2 ready
├── svc/checkout                 ✓ ClusterIP 80/TCP,9090/TCP, 2/2 pods ready
└── rs/checkout-6b8c             ✓ 2/2 ready, revision 2
    ├── pod/checkout-6b8c-aaaaa  ✓ Running
    │   ├── container main       ✓ running
    │   ├── cm/checkout-config   ✓ 2 keys
    │   └── secret/checkout-tls  ✓ kubernetes.io/tls, 2 keys
    └── pod/checkout-6b8c-bbbbb  ✓ Running
        ├── container main       ✓ running
        ├── cm/checkout-config   ✓ 2 keys
        └── secret/checkout-tls  ✓ kubernetes.io/tls, 2 keys
```

`✓` is ready, `✗` is not, and `?` means tug can't tell. Secrets show only their
key names, never their values.

Any other kind shows everything it owns, each with the health its status
conditions give it, and each workload it owns as above. `·` marks an object
that reports no health of its own, such as a Secret, which tug never reads:

```console
$ tug tree db/orders
database/orders                ✗ BackupFailing: the latest backup failed
├── backup/orders-nightly      ✗ UploadFailed: bucket "orders-backups" not found
└── secret/orders-credentials  ·
```

## Watch it change

`tug watch` follows a rollout, or any object's reconciliation, as it happens.
It starts with the object's state and whatever it owns that isn't ready, then
prints a line for each change that matters, marked as `tug tree` marks health:

```console
$ tug restart checkout
$ tug watch checkout --until ready
14:02:11 ✗ deploy/checkout  1/1 ready, 1 old (owns 4, 2 not ready)
14:02:11 ✗ pod/checkout-7f9d-ccccc  ContainerCreating
14:02:11 ✗ rs/checkout-7f9d  0/1 ready, revision 6
14:02:15 ✓ pod/checkout-7f9d-ccccc  became ready: Running
14:02:15 ✓ rs/checkout-7f9d  became ready: 1/1 ready, revision 6
14:02:15 ✗ deploy/checkout  1/1 ready, 1 old → 2/1 ready, 1 old
14:02:16 ✓ pod/checkout-6b8c-aaaaa  is terminating
14:02:16 ✓ deploy/checkout  Progressing is True (ReplicaSetUpdated → NewReplicaSetAvailable)
14:02:16 ✓ deploy/checkout  became ready: 1/1 ready
```

A container that restarts says how it last stopped (`container main restarted
(3 restarts), last exit code 137 (OOMKilled)`), and a pod no node can take
says why, as the scheduler does. For a custom resource, the lines are its
conditions changing (`Ready False → True (Issued: certificate is up to date)`),
its controller catching up with a new generation, and what it owns appearing
and changing; tug looks again from time to time for things it owns of kinds it
hasn't seen yet. Add `--events` for new warning events, marked `!`.

`--until ready` makes it a wait for scripts and CI: it exits 0 once the
rollout is done, and 1 if the job fails, the deployment passes its progress
deadline, or `--timeout` passes first. `--until deleted` waits for something to
be gone, and `-o json` writes one JSON object per change:

```bash
tug watch deploy/api --until ready --timeout 5m
tug watch job/migrate --until ready -o json | jq -r .message
```

## Send it to someone who can help

`tug support bundle` collects what someone helping you needs to see into one
redacted archive to attach to a ticket: the object and everything it owns as
YAML, `tug why` and `tug tree` as JSON, events, its containers' logs (the
previous run's too, when one restarted), the nodes its pods run on, the
cluster's version and resources, and `tug doctor`'s checks.

```console
$ tug support bundle deploy/api
discovering the cluster's resources…
reading deployment/api and what it owns…
reading events…
reading 2 nodes…
reading 4 logs from 2 pods…
running tug doctor's checks…
tug-bundle-prod-eu-deployment-api-20261121T153000Z.tar.gz
wrote 21 files (48.2 KiB before compression); review the bundle before you share it: its README.md says what was redacted
```

Name `namespace/<name>` for everything in a namespace, with a diagnosis of
each workload. Events and logs cover the last hour; change it with `--since`.

Redaction is always on. Secrets are copied from the metadata API, so no
Secret's data is in the bundle. Environment variable values, ConfigMap values,
fields named like a credential (`password`, `token`, `apiKey`) and kubectl's
last-applied annotation become `<redacted>`, and so do bearer tokens,
passwords in URLs, JSON Web Tokens, private keys and assignments such as
`password=...` in logs, events and every other text. Add your own patterns
with `--redact-pattern`, which may be repeated; the bundle counts them but
never records them.

Redaction can't know everything your applications treat as private, so review
the bundle before you send it. `--preview` lists every file it would write,
with its size and the API request it came from, and writes nothing;
`--exclude <kind>` leaves a kind out. Inside the archive, `README.md` says what
was redacted and how to search for what wasn't, and `manifest.json` lists each
file, where it came from and how many values were redacted from it. The archive
is readable by you only.

## Restart, scale and roll back

```bash
tug restart api              # rolling restart (deployments, statefulsets, daemonsets)
tug scale api 3              # set replicas (deployments, statefulsets)
tug scale worker 0           # scale to zero
tug rollback api             # back to the previous revision (deployments)
tug rollback api --to-revision 3
```

```text
Restarted deploy/api-server
Scaled deploy/api-server to 3
Rolled deploy/api-server back to revision 7
```

All three change the cluster, so on a read-only session tug asks first, or
refuses in a script.

## CPU and memory

```bash
tug top api                  # every pod of deploy/api-server
tug top                      # every pod in the namespace
```

`tug top` uses `kubectl top`, so it needs kubectl and the cluster's
[metrics-server](https://github.com/kubernetes-sigs/metrics-server).

## Open k9s

```bash
tug ui
```

Opens [k9s](https://k9scli.io) on this terminal's cluster and namespace.
