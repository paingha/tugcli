---
title: Quick start
description: Import your clusters, connect to one, and try the everyday commands. About five minutes.
icon: Rocket
---

This walk-through assumes you have [installed tug](/docs/getting-started/installation)
and [added the shell hook](/docs/getting-started/shell-setup). You'll need
access to at least one cluster: an existing kubeconfig, a local
[kind](https://kind.sigs.k8s.io/) or minikube cluster, or a cloud account.

<Steps>
<Step>

### Find your clusters

```bash
tug import
```

tug looks around your machine for places that know about clusters: kubeconfig
files, local tools such as kind and minikube, AWS profiles and gcloud
configurations. It shows what it found and asks which to import:

```text
Found these accounts:
   1) kubeconfig/default  /Users/sam/.kube/config
   2) local/kind
   3) aws/work
Import which? [all, or numbers like 1,3; none to cancel]:
```

Press <kbd>Enter</kbd> to import everything, or type numbers such as `1,3`.

```text
✓ kubeconfig/default: 3 clusters, 3 new, 2 credentials moved to keychain
✓ local/kind: 2 clusters, 2 new
✓ aws/work: 4 clusters, 4 new
```

“Credentials moved to keychain” means tug copied tokens it found in your
kubeconfig into your OS keychain. Your kubeconfig file is left exactly as it was.

</Step>
<Step>

### See what you have

```bash
tug ls
```

```text
  NAME        PROVIDER  ACCOUNT  REGION     VERSION  ENV      LABELS                       STATUS
  kind-dev    local     kind     -          v1.33.1  dev      distro=kind,local=true
  prod-eu     aws       work     eu-west-1  1.32     prod     aws-account-id=123456789012
  staging-us  aws       work     us-east-1  1.32     staging  aws-account-id=123456789012
```

The **ENV** column matters: clusters with `env=prod` open read-only. tug fills
it in from the provider, or guesses it from the name: `prod-eu` contains
`prod`, so it's treated as production.

</Step>
<Step>

### Connect this terminal

```bash
tug connect staging
```

You don't need the full name. tug matches what you type (here, `staging-us`).
If several clusters match equally well, it shows a numbered list to pick from.

```text
Connected to staging-us, namespace default, read-write
```

Your prompt now starts with `⎈ staging-us:default`. Open a second terminal and
it's still disconnected: **each terminal has its own session**.

</Step>
<Step>

### Use your usual tools

kubectl, helm and k9s already follow the session:

```bash
kubectl get pods
helm list
tug ui            # opens k9s on this cluster
```

Anything tug doesn't know runs as kubectl, so this works too:

```bash
tug get pods -A
```

</Step>
<Step>

### Pick a namespace

```bash
tug ns pay        # fuzzy: finds "payments"
tug ns            # no name: choose from a list
```

</Step>
<Step>

### Try the everyday commands

```bash
tug logs api -f     # follow logs from every pod of deploy/api-server
tug sh api          # open a shell in one of its pods
tug pf api 8080     # forward localhost:8080 to it (Ctrl-C to stop)
tug restart api     # rolling restart
tug top api         # CPU and memory per pod
```

The [workloads guide](/docs/guides/workloads) covers each one.

</Step>
<Step>

### Visit production safely

```bash
tug connect prod
```

```text
Connected to prod-eu, namespace default, read-only (tug unlock 15m to allow writes)
```

The prompt turns **red**. tug's own commands, and kubectl commands you run
through `tug`, now ask before changing anything. When you really do need to
make a change:

```bash
tug unlock 15m      # writes allowed for 15 minutes; the prompt turns yellow
tug lock            # done early? lock it again now
```

<Callout type="warn">
  Plain `kubectl` talks to the cluster directly, so the read-only guard only
  covers it when you connect with `--proxy`. See
  [Read-only sessions](/docs/concepts/read-only) for the full picture.
</Callout>

</Step>
<Step>

### Disconnect

```bash
tug disconnect
```

The terminal goes back to whatever `KUBECONFIG` it had before. Closing the
terminal does the same.

</Step>
</Steps>
